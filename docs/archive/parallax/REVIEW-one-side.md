# One Side pre-build review — verdict & plan

## Verdict: FIX-FIRST

The synthesised plan is directionally right and I verified its factual spine against 9d0c2af: markBridgeSent really does fire on Copy (src/features/refocus/steps/ResultStep.tsx:177) and really does arm a check-in that "both partners read" (supabase/migrations/0044_repair_checkin_lifecycle.sql:19-21); the tool schema really does make no-bridge impossible (REFLECTION_TOOL requires bridge); solo rows really are author-only under RLS (0039_refocus_solo_persist.sql:39-51) and are excluded from get_couple_context because only writeBackSummary (mediation-only) sets summary and 0048 filters on `summary is not null` — so the plan's core moves (sever check-in, READ_TOOL with bridge_decision, v2 body branching, cut mic/streaming/Tier-2, sealed note first) are sound and its conflict resolutions all picked the evidence-backed side. But it cannot ship as written because its DELIVERY path is broken: evening 4 says "ships as an OTA update to build 18 via expo-updates (same runtimeVersion)". expo-updates channels are baked into the binary; build 18 is on channel "production" (eas.json) with runtimeVersion policy appVersion = 2.0.1 (app.json). An `eas update` on that channel+runtime converts EVERY 2.0.1 install into One Side — Dani's phone and any internal tester — not just Yash's. There is no per-user OTA. The only safe ships are EAS build 19 on a new channel (e.g. "oneside", internal distribution — the plan's "or build 19 if preferred" must become the ONLY option, with the channel change) or verified certainty that no other device runs 2.0.1. Second fix-first: the 20-fixture offline eval "curl'd against the deployed function" will be rate-limited at fixture 13 — claim_refocus_slot is per-user (index.ts:192-206, 12/hr per 0012); the eval needs spacing, multiple test users, a temporary limit bump, or (better) running the same prompt+tool directly against the Anthropic API from a script. Third: the plan names "Dani, or a fresh Claude session" as the blind-read shuffler — Dani reading ten raw-ish outputs about five real fights with her is both an experiment contaminant and a relationship incident; it must be a fresh Claude session only. Fourth, smaller: evening 2 rewrites crisisResult/abuseResult copy in place, but v2.0.0 is in App Store review with auto-release (commit 096759b) and the legacy couples path serves the same constants — the safety copy must be v-branched like the schema, or the couples app shows one-person copy to reviewers/users. All four are hours of fix, not a re-plan; hence FIX-FIRST, not STOP.

## Top three
1) SENT-MEANS-COPIED + PARTNER-VISIBLE SIDE EFFECT (consistency audit + red team, both BLOCKER). The test's key metric is stamped on Copy (ResultStep.tsx:177 → refocusActions.ts:99-106 → mark_bridge_sent), which both falsifies the pass condition ("copied-but-not-sent is a fail", PRD §7) and arms a repair check-in projected to BOTH partners (0044:19-21) — the one-person app would ping the partner. This is the single most dangerous finding because it silently corrupts the experiment AND violates the product's core promise. Plan addresses it: YES, fully — Copy records 'copied' only, markBridgeSent severed, manual "I sent it" toggle in Receipts, and the sever is in the definition-of-done smoke list. 2) THE PASS CONDITION PUNISHES NO-BRIDGE (red team BLOCKER). §3 makes deflation first-class; §7's "≥2 bridges sent of 5 frictions" structurally rewards over-producing bridges — the app's one real product idea is scored as a failure mode. Plan addresses it: YES — denominator changed to bridge-offering runs, separate blind judgment of each no-bridge call, sealed before the first commit as owner decision 4 (correctly marked MUST-approve). 3) THE EDGE FUNCTION CANNOT EXPRESS THE PRODUCT (consistency + prompt review, BLOCKER). REFLECTION_TOOL requires a non-empty bridge (index.ts:397-404) and handleSolo 502s without one, so "there is no bridge here" can only surface as an error; the shape (happened/angles/wayback) is the wrong register for the (a)/(b)/(c) triad. Plan addresses it: YES and well — single forced READ_TOOL with bridge_decision listed first, empty-string convention (right call for Haiku forced-tool reliability), server deletion of half-written bridges on no_bridge, validateBridge with retry-then-502, and v2-body branching so build 18 keeps working. The one gap inside this fix is noted above: the safety-copy constants are shared with the legacy path and are not v-branched in the plan.

## What everyone missed
The class nobody was assigned is DEPLOYMENT BLAST RADIUS AND EXPERIMENT CONTAMINATION IN A SHARED PROD ENVIRONMENT — six reviewers treated this as a one-user build, but it ships into a backend and update channel shared with the partner, other testers, and an in-flight App Store review. Concretely: (a) OTA cannot be scoped to one user — eas.json puts build 18 on channel "production" and app.json's runtimeVersion policy is appVersion (2.0.1), so the plan's "OTA to build 18" ships One Side to every 2.0.1 install including Dani's; must be EAS build 19 on a fresh channel. (b) v2.0.0 is in App Store review RIGHT NOW with auto-release on approval (commit 096759b) — the couples app could go live to strangers mid-test against the rewritten edge function; the plan v-branches the schema but not the crisis/abuse copy constants the legacy path serves. (c) Dani as blind-read shuffler hands the partner the raw material of five fights about her — the plan's own fix for the non-blind read creates a worse problem; Claude-session only. (d) The 20-fixture eval dies at fixture 13 on the per-user 12/hr limit (claim_refocus_slot, index.ts:192-206) — an evening-4 stall nobody priced; run the eval against the Anthropic API directly, not through the deployed function. Two things I verified that reviewers ASSERTED but did not prove, which happily hold: solo rows are genuinely author-only under RLS (0039:39-51), and solo sessions genuinely cannot leak into Dani's mediation context because only writeBackSummary (mediation path only) writes summary and get_couple_context filters `summary is not null` (0048:108-113) — so the fixture/test entries about Dani stay invisible to her client. One residual nobody named: the plan persists raw fight drafts to AsyncStorage on every keystroke with no deletion story in the test build (Settings-delete was cut) — for a public-repo, privacy-positioned product, note in the sealed doc that drafts are purged on success and add a manual purge before rung 3.

## Late risk
Evening 4. It is the plan's own admitted spill point ("most likely to spill") and it now hides two unpriced discoveries: the eval stalling on the 12/hr per-user rate limit at fixture 13, and — when the OTA-to-build-18 plan is discovered to be unscopable — an unplanned EAS build 19 on a new channel plus TestFlight processing plus the physical-device smoke loop, all stacked on Receipts (a genuinely new user-scoped surface), the ~5-suite test sweep, and hand-scoring 20 eval outputs. Fix by re-sequencing, not adding hours: kick off EAS build 19 (new channel, no native changes needed) on the Day-0 afternoon so TestFlight processing runs in parallel with the week's JS work, and run the eval as a direct Anthropic API script the moment the prompt is settled on evening 2, not after the client work on evening 4.

## Test risk
The blind read. Even with the plan's re-templating fix, it is structurally unblindable: Yash lived the five fights, read all ten outputs at generation time, and the app output carries fingerprints (sub-40-word bridge, no-em-dash rule at index.ts, the fixed triad) against freeform ChatGPT — at n=5 with a 4/5 bar, a knowing reader produces whatever verdict he is primed toward, and the self-experimenter wrote the PRD, the prompt, AND the scoring rules. If the head-to-head cannot be made blind it is theatre, and a false "the app reads better" pass is worse than no test — it green-lights rung 2 (Dani) on contaminated evidence. Mitigation the sealed note should add: demote the blind read to secondary/informational, and make the primary verdict the behavioural metrics that cannot be gamed by memory — unprompted opens at real frictions over three weeks, drafts abandoned mid-capture, bridges manually marked sent, and the brutal pre-registered stop condition the PRD already contains ("writing it out helped; I skimmed the output"). Behaviour is the honest instrument here; judged quality is not.

## Honest total
The PRD's 'one afternoon plus roughly four evenings' is dead AS WRITTEN — the effort review's 24-32h (seven to nine evenings) is right for the full spec, because the PRD silently includes a native build cycle (mic), an SSE streaming stack, Tier-2, true account-lessness, and a Result screen that is not actually settled. WITH the cut list adopted here (keyboard dictation instead of the native pill, streaming cut, Tier-2 deferred, existing session kept, Settings-delete cut, Result honestly budgeted, compressed eval kept), the plan above totals ~22-25h: one 4h afternoon plus four 4-6h evenings, with a named buffer evening 5 for eval-driven prompt iteration on (b) and the device loop. Call it: afternoon + four evenings + one buffer evening, and the buffer is real — if the offline eval shows (b) isn't specific from one short account, spend evening 5 on the prompt before the first paired run rather than shipping the test's least-evidenced assumption unexercised.
